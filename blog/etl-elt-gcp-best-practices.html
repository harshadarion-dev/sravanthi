ETL vs ELT on Google Cloud Platform: Architecture Patterns for 2025

By Sravanthi Maha · Apr 10, 2026 · 10 min read

One of the most common architectural decisions in cloud data engineering is choosing between ETL (Extract, Transform, Load) and ELT (Extract, Load, Transform). On Google Cloud Platform, this translates concretely to: Dataflow ETL vs. BigQuery ELT. After architecting both at Wells Fargo, Amazon, and Verizon, here's my decision framework.

What Changed: Why ELT Became Dominant

Traditional ETL (transform before loading) made sense when storage was expensive and compute was cheap relative to I/O. Modern cloud data warehouses like BigQuery flipped this equation — storage is nearly free ($0.02/GB/month) while compute scales on-demand. This makes ELT — loading raw data first, then transforming in-warehouse — economically and operationally superior for most analytical workloads.

ETL with Dataflow: When to Use It

Choose Dataflow ETL when:

  • You're processing streaming data (Pub/Sub → Dataflow → BigQuery) where transformation must happen in-flight
  • You need to mask/tokenize PII before any storage (compliance requirement)
  • Your transformation logic requires stateful processing (session windows, custom aggregations)
  • Source data volume is so large that loading raw data first would be cost-prohibitive
  • You need cross-source joins during ingestion (enriching events with API lookups)
# Dataflow ETL: Real-time PII tokenization + enrichment
import apache_beam as beam

class TokenizePII(beam.DoFn):
    def process(self, element):
        element['ssn'] = tokenize(element['ssn'])
        element['email'] = hash_email(element['email'])
        yield element

pipeline = (

ELT with BigQuery: When to Use It

Choose BigQuery ELT when:

  • Transformation logic can be expressed in SQL (dimensional modeling, aggregations, joins)
  • You want analysts to query raw data for ad-hoc exploration alongside curated marts
  • You're running batch workloads where transformation latency of minutes is acceptable
  • You want transformation versioning via dbt or SQL migration scripts
  • Cost optimization is paramount — BigQuery ELT is typically 60-80% cheaper than equivalent Dataflow jobs
-- BigQuery ELT: Transform raw → curated in SQL
CREATE OR REPLACE TABLE `project.curated.daily_sales` AS
SELECT
  DATE(order_timestamp) AS order_date,
  product_id,
  SUM(revenue) AS total_revenue,
  COUNT(DISTINCT customer_id) AS unique_customers,
  AVG(order_value) AS avg_order_value
FROM `project.raw.orders`
WHERE order_status = 'completed'
  AND DATE(order_timestamp) >= DATE_SUB(CURRENT_DATE(), INTERVAL 90 DAY)
GROUP BY 1, 2;

The Hybrid Pattern: What We Use at Enterprise Scale

At Wells Fargo, we use a hybrid Lambda Architecture where both paradigms coexist:

  1. Speed Layer: Pub/Sub → Dataflow (ETL, PII masking) → BigQuery streaming buffer → real-time dashboards
  2. Batch Layer: GCS raw files → BigQuery Load Jobs (ELT, no transformation) → dbt transforms → data marts
  3. Serving Layer: BigQuery materialized views merge speed + batch layers for consistent querying

FAQ

Should I use ETL or ELT on Google Cloud Platform?

Use ETL (Dataflow) for streaming data, PII masking before storage, or complex stateful transformations. Use ELT (BigQuery SQL) for batch analytical workloads, SQL-expressible transforms, and when cost optimization is a priority. Most enterprise architectures use a hybrid of both.

What is the cost difference between ETL and ELT on GCP?

Dataflow ETL costs scale with vCPU hours and shuffle data volume. BigQuery ELT costs scale with bytes scanned. For analytical workloads, BigQuery ELT is significantly cheaper. For high-volume streaming pipelines, Dataflow becomes cost-competitive.
